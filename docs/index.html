§ 01The core idea

A .pptx is a zip of XML.
There were two bad ways in.

You see a slide. The agent gets a ZIP file — one ordinary slide is about 2,000 lines of OOXML. hands-on-deck takes a third path.

Hand-write OOXML fragile

Unzip, edit slide3.xml raw, rezip. Thousands of tokens on angle brackets; one bad namespace and PowerPoint refuses the file.

Regenerate from scratch lossy

Rebuild with a generation library — and lose the master, the theme, every designer decision the template encodes.

Declarative patch hands-on-deck

The agent writes a JSON patch describing intent. The tool validates everything, then executes atomically.

the LLM compiles intent; the tool does the bytes. The LLM never edits XML.

patch.json 
{"ops": [
  {"op": "replace-text",
   "scope": "master", "from": "Globex", "to": "Acme"},
  {"op": "set-text",
   "slide": 3, "shape": "s12", "text": ["Q3 results", "Tokens down 84%"]},
  {"op": "swap-image",
   "slide": 4, "shape": "s9", "image": "screenshot.png"},
  {"op": "duplicate",
   "slide": 5, "shape": "s31", "offset": [0, 1.2], "text": ["Fourth pillar"]}
]}

replace-text · scope: master

Rebrand the whole deck — masters, layouts, every slide — in one op.

set-text

Address a shape by its stable id; formatting survives.

swap-image

New picture, same frame, same crop. The layout never knows.

duplicate

Clone a styled shape, offset in inches, rewrite its text. The template is the design system.

deck.py deck.pptx apply patch.json --fix --render img/
— validated first, applied atomically, linted after.

/failure mode: no spatial sense

The linter watches the agent's hands

Agents can't feel overflow or collision. After every apply, the linter reports only what the patch broke — exact inches, exact fix command, no noise about pre-existing quirks.

§ 02The create path · new

Write the slide as a webpage.
Ship it as a slide.

HTML/CSS is the layout language agents know best. html2patch renders your slide in a headless browser and compiles every measured box into a deck.py patch. The browser measures; deck.py stays the only writer.

slide.html → patch.json → deck.pptx 
<h1>The deck builds <em>itself</em> now.</h1>
<div class="card">…gradient, radius, flexbox…</div>
<img style="object-fit:cover" src="chart.png">

$ python html2patch.py slide.html --deck deck.pptx
  → patch.json: 23 ops (add-slide, add-shape, add-picture…)
$ python deck.py deck.pptx apply patch.json --render img/
  ✓ applied atomically · linted · rendered for your own eyes

One writer

A compiled slide is born with the same shape ids, lints, and diff as every edit — nudge one box seconds after creating it.

Creates into your template

add-slide onto your branded master's layouts. Free-form design inside your own deck — the thing generate-a-new-file architectures can't do.

§ 03The comparison

Same job. Different machinery.

Anthropic's pptx skill puts its guardrails in advice to the model — ignored on exactly the slide that matters. Ours are machinery in the tool.

the moment
Anthropic's pptx skill
hands-on-deck
Make an edit
Unpack the zip, hand-edit slide3.xml raw — the skill's own docs list the OOXML pitfalls to dodge while you type angle brackets.
Declare the op. set-text inherits the old text's formatting; swap-image keeps frame and crop. The XML is the tool's problem.
Get it wrong
Validation runs at pack time — after all the editing. Errors arrive late, one repack per discovery, and the tree on disk is already half-edited.
Patch rejected before a byte is written — every error at once, with the slide's real shape inventory in the message. The agent repairs in one pass.
